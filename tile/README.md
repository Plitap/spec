# PLITAP — структура плитки и словарь полей

**Draft 0.1 · 16.09.2026**

**Автор идеи:** Bogom ([Bogom@vk.com](mailto:Bogom@vk.com))

## Статус документа

Черновик структуры плитки PLITAP для открытого обсуждения. Документ описывает разделы, поля и их назначение. До утверждения первой стабильной версии состав полей может изменяться по результатам обсуждения и проработки типов плиток.

Поддержка отдельных возможностей клиентами определяется отдельно.

## Как читать документ

Обязательность поля относится к описываемому объекту. Например, обязательное поле события не означает, что каждый пакет должен содержать всю историю событий.

Таблицы описывают логическую структуру. Точные типы данных, кодирование, ограничения размеров, правила отсутствующих значений и области хеширования и подписей определяются в спецификации формата данных. Неопределённые детали отмечены в описаниях полей.

## 1. Модель и границы

Плитка имеет неизменяемый паспорт, сетевой идентификатор выпущенного экземпляра, состояние, историю, содержимое, вложения, правила и доказательства. Копия пакета не создаёт второго владельца.

| Раздел | Назначение |
|---|---|
| `header` | Упаковка и каталог разделов |
| `genesis` | Неизменяемый паспорт |
| `state` | Актуальное принятое состояние |
| `head` | Хеш состояния и связь с историей |
| `events` | Принятые события или достаточные проверяемые свидетельства |
| `content` | Публичная по умолчанию страница, материалы и защищённая часть |
| `objects` | Pt и другие учитываемые вложения |
| `proofs` | Подписи и доказательства |
| `definitions` | Точные определения форматов, типов и правил |
| `delivery` | Необязательный контекст конкретной передачи |

`rules` ниже — отдельное логическое описание правил, связанное через `rules_hash` и определения. Оно не вводит автоматически одиннадцатую обязательную секцию контейнера.

**Общий формат, сеть и клиент — три уровня.** Общий формат допускает отсутствие координат; конкретная сеть, тип или клиент могут требовать их для действий. Клиент выбирает поддерживаемые сети и приём плиток, включая тестовые. Оплата выпуска не заменяет проверку структуры, полномочий и применимых правил. Домены/IP — точки подключения, не достаточное доказательство идентичности сети.

**Чтение и исполнение различаются.** Клиент может безопасно показать базовое содержимое, не умея выполнять конкретную операцию. Незнакомое обязательное правило нельзя молча игнорировать при действии.

## 2. Общие значения

| Значение | Состав | Смысл |
|---|---|---|
| `DefinitionRef` | `id`, `version`, `hash` | Точное неизменяемое определение |
| `HashRef` | `algorithm`, `value` | Алгоритм с параметрами и значение хеша |
| Типизированное расширение | Идентификатор, версия, защищённые данные/их хеш, применимость | Дополнение с понятной областью обязательности; точные имена предстоит выбрать |
| `Location` | `frame`, `coordinates`, `accuracy_m`, `measured_at`, `source`, `subject_id`, `proof_refs` | Описание координат; обязательность элементов и состав доказательств уточняются |

`id` — идентичность, `hash` — связь с точными данными, `version` — версия определения, `revision` — номер состояния экземпляра. Ключ пользователя может меняться без смены его идентичности.

## 3. Паспорт и выпуск

Окончательный `tile_id` возникает только при успешном оплаченном выпуске в сети. Локальная заготовка ещё не является выпущенным экземпляром. `genesis_hash` можно вычислить локально; доказательство выпуска связывает его с `tile_id` и принятой регистрацией. Механизм подтверждения выпуска определяется спецификацией сети.

| Значение | Обязательность | Где определяется |
| --- | --- | --- |
| `tile_id` | Да для выпущенного экземпляра | Результат выпуска, события и ссылки; единственное каноническое место в упаковке ещё не выбрано |
| `genesis_hash` | Да для проверки выпуска | Вычисляемое значение и ссылки на паспорт |
| Доказательство выпуска | Да для выпущенного экземпляра | `proofs` |

`tile_id` исключён из хешируемого тела `genesis`. Подписи, использующие этот ID, также не входят в исходное тело. Два отдельно принятых выпуска одинакового содержания должны различаться, а повтор одной операции — возвращать её результат. Способ различения экземпляров с одинаковым паспортом требует уточнения.

### Поля `genesis`

Все присутствующие поля паспорта неизменяемы; подпись/доказательство выпуска защищает связь с его хешем.

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `origin_id` | ID среды | Да | Исходная сеть или среда выпуска. Межсетевые переходы в этой редакции не определены. |
| `protocol` | DefinitionRef | Да | Протокол создания. |
| `type` | DefinitionRef | Да | Тип плитки и его точное определение. |
| `creator_id` | ID участника | Да | Создатель исходного объекта; не обязательно настоящее имя. |
| `issuer_id` | ID участника | Да | Выпустивший этот экземпляр; может совпадать с создателем. |
| `created_at` | Время | Да | Заявленное время создания; не заменяет сетевое время принятия. |
| `created_place` | Location | Нет в общем формате | Место создания; требования присутствия определяет профиль. Семантика неизвестно/не раскрывается ещё уточняется. |
| `content_hash` | HashRef | Да | Исходное содержимое. |
| `rules_hash` | HashRef | Да | Исходные применимые правила. |
| `source` | Ссылка и основание | Условно | Для выпуска из шаблона/другой плитки: точный источник и разрешение. |
| `series` | Описание серии | Условно | Для серий: ID, номер экземпляра, ссылка/хеш определения серии. |
| `extensions` | Набор расширений | Нет | Дополнительные неизменяемые данные. |

## 4. Текущее состояние — `state`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `revision` | Целое | Да | Номер принятого состояния; увеличивается при его изменении. |
| `owner_id` | ID участника | Для активной плитки | Текущий владелец. Значение при завершении жизненного цикла открыто. |
| `control` | Профиль полномочий | Да | Публичные условия управления; секретных ключей здесь нет. |
| `control_version` | Целое | Да | Версия полномочий при ротации/восстановлении. |
| `rules_hash` | HashRef | Да | Действующие правила; меняется только при разрешённом переходе. |
| `content_hash` | HashRef | Да | Актуальное содержимое. |
| `objects_hash` | HashRef | Да | Актуальный состав вложений. |
| `extensions` | Набор расширений | Нет | Дополнительное каноническое состояние, когда существующих полей недостаточно. |

Изменения принимаются по правилам операций. `balance`, `rating`, `weight`, `active`, `sending` не вводятся как независимая истина. Баланс и доступность действий вычисляются. До завершённой передачи владельцем остаётся отправитель.

### Связь состояния и истории — `head`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `state_hash` | HashRef | Да | Хеш тела состояния, связанный с экземпляром. |
| `last_event_hash` | HashRef | Для принятого состояния | Хеш события, установившего это состояние. |

Оба поля находятся вне хешируемого тела `state`: циклического вычисления быть не должно.

## 5. Содержимое — `content`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `format_version` | Версия | Да | Версия описания содержимого. |
| `title` | Текст | По типу | Название; не обязательно для всех типов. |
| `language` | Языковое описание | Условно | Для языковых материалов; локализации и точная структура открыты. |
| `preview` | Описание представления | Нет | Предпросмотр; при отсутствии клиент показывает стандартное представление. |
| `blocks` | Упорядоченный список | Для типа со страницей | Текст и другие элементы в порядке показа. Схемы видов блоков ещё предстоит описать. |
| `parts` | Список материалов | Условно | Данные, используемые блоками: изображения, видео, документы и т. д. |
| `protected_parts` | Список защищённых материалов | Нет | Отдельно зашифрованное содержимое. |

Содержимое публично по умолчанию: доступно без секрета, но не обязано находиться в реестре или на каждом узле. Пропорции предпросмотра определяет клиент. При раскрытии показывается страница с прокруткой. Основной текст представлен текстовыми элементами `blocks`.

Кнопка «Получить» принадлежит клиенту и размещается после обязательного содержимого. Открытие и просмотр не меняют владельца. После нажатия клиент подписывает принятие; завершение владения требует принятия операции сетью. Требования показа описывает профиль: отображение обязательного содержания и достижение конца страницы, но не доказательство чтения или понимания человеком. Для видео/аудио требования ещё не выбраны. Лимиты текста, блоков и материалов задаются типом; численные значения не выбраны.

### Материал в `parts`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `id` | ID части | Да | Локальная ссылка внутри содержимого. |
| `role` | Назначение | Да | Роль материала. |
| `media_type` | Тип данных | Да | Формат материала. |
| `hash` | HashRef | Да | Целостность точных данных; охват шифрования/сжатия уточняется. |
| `size` | Размер | Да | Единицы и то, какой размер считается, уточнятся в машинном формате. |
| `encoding` | Описание | При применении | Дополнительное кодирование. |
| `compression` | Описание | При применении | Сжатие. |
| `encryption` | Описание | При применении | Шифрование без открытых секретных ключей. |

### Доступ к `protected_parts`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `access_mode` | Режим | Да для защищённой части | Только получатель либо дополнительный отдельно переданный секрет; точные значения не выбраны. |
| `encryption` | Описание защиты | Да для защищённой части | Алгоритм/параметры и необходимые открытые материалы. |
| `Ссылка на ключ получателя` | Ссылка | Для режима получателя | Точное имя поля и привязка при последующей передаче ещё открыты. |
| `Параметры дополнительного секрета` | Описание | Для режима с кодом | Секрет может прийти, например, по почте; сам секрет не публикуется. |

Общие сведения о блоках не должны дублироваться конфликтующими описаниями в `parts` и `protected_parts`: точную нормализацию ещё нужно выбрать. Получить плитку можно до получения внешнего кода. Требование просмотра не означает обязательного раскрытия всех секретных вложений до принятия. Хеш простого секретного значения может раскрывать его перебором; выбор защищаемых байтов и commitments относится к отдельной криптографической спецификации.

Узел может хранить доступную часть или зашифрованные блоки по собственной политике и обозначать неполноту копии. Политика хранения определяется узлом и применимой сетью.

## 6. Вложения — `objects`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `object_id` | ID | Да | Идентичность вложения по его типу. |
| `type` | DefinitionRef | Да | Тип объекта. |
| `asset_id` | ID ресурса | Для ресурсов | Однозначно различает валюты/ресурсы; имя «Pt» не является доказательством подлинности. |
| `amount` | Количество | Для количественных объектов | Точные диапазоны/представление — отдельно; текущая база Pt предусматривает целые единицы. |
| `data_hash` | HashRef | При наличии данных | Специфические данные и состояние объекта. |
| `binding` | Правило связи | Да | Связь с плиткой, извлечение/разделение только в пределах правил. |
| `proof_refs` | Ссылки | По типу | Выпуск, права, допустимые изменения и другие доказательства. |

Отдельный срок вложенного права в базовую оболочку не вводится: заявленные права должны действовать, пока действительна плитка. Исполнение внешнего обещания магазином не обеспечивается одной подписью; нарушение относится к доверию к отправителю. Секретный промокод может быть содержимым; учитываемое право требует своего типа объекта. Обесценивание не считается жалобой или отрицательным рейтингом. Минимальная принимаемая ценность — настройка клиента. Экономика Pt отложена.

## 7. Правила — `rules`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `issue` | Группа правил | Да | Выпуск, копирование и тираж. |
| `transfer` | Группа правил | Да | Передачи и их ограничения. |
| `value` | Группа правил | По вложениям | Пополнение, обесценивание, извлечение. |
| `lifecycle` | Группа правил | Да | Сроки действия и завершение. |
| `content` | Группа правил | Да | Режимы изменения частей. |
| `client` | Группа правил | При специальных требованиях | Возможности клиента и подтверждения по действиям. |
| `upgrade` | Группа правил | Да | Разрешение и пределы изменения самих правил. |

Правила могут задаваться определением типа и параметрами экземпляра; итог должен быть однозначен. В отсутствие явного разрешения изменение содержимого и правил не разрешается. Обязательность группы логическая, не требование дублировать весь текст в каждом пакете.

### `rules.lifecycle`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `mode` | Режим | Да | Бессрочно / длительность после получения / фиксированное окончание. |
| `duration` | Длительность | Для относительного срока | Для обычных типов предложен минимум час после получения; исключения типов ещё прорабатываются. |
| `expires_at` | Время | Для фиксированного срока | Дата окончания. Минимум двое суток не утверждён. |
| `start_event` | Определение события | Для относительного срока | Первое или каждое получение — открыто. Фактическая привязка времени требует события/состояния. |
| `on_expire` | Правило | Для ограниченного срока | Какие права прекращаются; сохранение архива не равно активности. |

### `rules.transfer`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `modes` | Список | Да | Адресная и/или радиусная передача. |
| `recipient_policy` | Правило | При ограничениях | Постоянные требования к получателю. |
| `location_policy` | Правило | При требованиях | Чьё место, для каких действий, точность/свежесть/доказательства. |
| `acceptance_policy` | Правило | По профилю | Требования принятия, включая показ клиентом. |
| `min_remaining_lifetime` | Длительность | Нет | Возможность порога остатка срока. Значение сутки — гипотеза, не общее правило. |

### Правило части в `rules.content`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `target` | Ссылка на часть | Да для правила | К чему применяется правило. |
| `mode` | Режим | Да для правила | `immutable`, `editable`, `append_only`. |
| `authority` | Полномочия | Да для правила | Кто вправе действовать; текущий владелец только в разрешённых частях. |
| `constraints` | Ограничения | При наличии | Размеры, форматы и другие пределы. |

Для `append_only` предусматриваются новые дополнения без удаления/перезаписи принятых записей. Структура записей дополнения определяется отдельным профилем. Переключение правил не должно неявно обходить неизменяемость ранее принятых частей; условия допустимой миграции ещё нужно определить.

## 8. История — `events`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `protocol` | DefinitionRef | Да | Версия правил конкретного события. |
| `network_id` | ID сети | Да | Сеть принятия. В текущей модели соответствует исходной сети плитки. |
| `operation_id` | ID операции | Да | Идемпотентность и связь частей действия. |
| `tile_id` | ID плитки | Да | Экземпляр. |
| `genesis_hash` | HashRef | Да | Точный паспорт. |
| `action` | Вид действия | Да | Выпуск, передача, пополнение, обесценивание, изменение и другие версионированные действия. |
| `previous_event_hash` | HashRef | Кроме первого | Предыдущее принятое событие. |
| `before_hash` | HashRef | Кроме создания | Изменяемое состояние. |
| `request` | Запрос/основание | Да логически | Инициатор, условия, разрешённое действие; форма автоматических действий открыта. |
| `result` | Результат | Да | Принятые изменения и контекст. |
| `after_hash` | HashRef | Да | Итоговое состояние; представление завершённой плитки уточняется. |
| `location` | Location | По профилю | Место действия конкретного участника; точный подписной охват открыт. |

`request`: `actor_id`, условные `recipient_id`, `data`, `expires_at`, `policy_hash`. `result`: `effects`, `context`. Подтверждённое время/порядок принятия отделены от времени клиента. Принятые события не редактируются; исправление — новое допустимое событие. Просмотр, транспорт и копирование не считаются каноническими изменениями сами по себе. Последнее место отправки определяется по передаче, не по произвольному последнему событию.

Неполная история обозначается как неполная. Правила допустимого сокращения и необходимых свидетельств ещё открыты; один хеш отсутствующей истории не заменяет её факты.

## 9. Доказательства — `proofs`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `type` | Версионированный тип | Да | Назначение, формат и правила проверки. |
| `subject_hash` | HashRef | Да | Точные подтверждаемые данные. |
| `data` | Типизированные данные | Да | Само доказательство. |
| `signer_id` | ID участника | Для подписного | Кто подписал. |
| `key_id` | ID ключа | Для подписного | Каким ключом. |
| `algorithm` | Алгоритм и параметры | Для подписного | Способ проверки. |
| `signature` | Подпись | Для подписного | Значение подписи. |
| `verification_material` | Проверочные материалы | По профилю доказательства | Открытые ключи и необходимые свидетельства, непосредственно или по проверяемым ссылкам. |

Точная вложенность подписных полей относительно `data` ещё выбирается: не хранить две независимые конфликтующие копии. Способ адресации из `proof_refs` также открыт.

Предусмотрены доказательства выпуска, выпускающего, разрешения исходного автора, полномочий владельца, принятия получателем, клиента, сетевого результата, игровых неизменяемых свойств и географии. Они не обязательны все сразу: состав определяется действием и профилем. Сведения клиента: ID, версия, сборка и подтверждение установленной процедуры. В применимом профиле доказательство клиента требуется при выпуске и каждом инициированном клиентом изменении состояния. Подтверждение просмотра является одной из его функций.

Подпись не равна полномочию. Неподдерживаемое, непроверенное и доказанно неверное различаются. Автономному архиву нужны необходимые материалы, а не только URL. Криптографическая долговечность, отзыв и обновление доказательств — отдельная задача.

## 10. Определения — `definitions`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `ref` | DefinitionRef | Да | ID, версия, хеш определения. |
| `kind` | Категория | Да | Протокол, тип, правило, формат вложения/доказательства и т. д. |
| `format` | Формат описания | Да | Как читать определение. |
| `body` | Точные данные | Для автономного архива | Содержимое определения; в передаче допустим проверенный локальный экземпляр/доступный блок. |
| `dependencies` | Ссылки на определения | При наличии | Нормативные зависимости. |

Точное описание `ref.hash` не должно включать само себя. Перечень хешируемых полей определения, в том числе связей с зависимостями, открыт.

Утверждённые версии определений неизменяемы; исправление получает новую версию. Метаданные словаря могут указывать введение поля, нежелательность использования и замену. Их не нужно повторять в каждой плитке. Хеш определения не делает его доверенным или исполнимым автоматически.

## 12. Предложение передачи — `delivery`

| Поле | Логический вид | Обязательность | Назначение и условия |
| --- | --- | --- | --- |
| `offer_id` | ID | Да при предложении | Конкретное предложение. |

| `mode` | Режим | Да при предложении | Адресный или радиусный. |
| `recipient_id` | ID участника | Адресно / при закреплении | Назначенный получатель. |
| `distribution_areas` | Список зон | При радиусном предложении | Одна или несколько областей. |

| `proof_refs` | Ссылки | Да при предложении | Разрешение отправителя и применимые подтверждения. |

Вложенность полей предложения и закрепления получателя требует уточнения. Таблица описывает необходимые данные, а не окончательную структуру подписываемого сообщения.

Радиусные условия подписываются до выбора получателя. Последующее закрепление требует отдельного подтверждения, не изменения подписанных байтов. Разделение на неизменяемое предложение и запись закрепления ещё нужно оформить. Секреты доступа к контенту не смешиваются с транспортным шифрованием пакета.

У одного экземпляра одно действующее закрепление за получателем. Чужие зашифрованные пакеты могут ретранслироваться/кешироваться без отображения как принадлежащие узлу плитки. До принятия владельцем остаётся отправитель. По истечении закрепления возможна новая попытка; общий предел серии попыток не выбран. Тарифы отзыва и запроса статуса определяются отдельно в правилах операций. Сам по себе пакет не удостоверяет завершение передачи.

## 13. Совместимость на десятилетия

Цель: базовые поля и доступное содержание плиток утверждённых версий должны безопасно читаться последующими совместимыми клиентами, в том числе через 100 лет. Старый клиент должен уметь читать сохранённое базовое представление новых плиток в пределах общего базового формата и безопасно обходить неизвестное. Для этого нужны стабильная базовая упаковка, ограничения расширений и тесты; детали ещё предстоит выбрать.

После стабильной v1 поля не удаляются и не переосмысливаются. Допустимы отметка нежелательности для новых данных и рекомендуемая замена. Расширения не могут молча изменять старый смысл. Сохранённые экспериментальные образцы должны обозначать точную редакцию и получать явно описанный путь архивного чтения.

Архивное чтение не требует исполнения вложенного кода, не восстанавливает истёкшие права и не доказывает актуальное владение. Сохранность самих данных/ключей/определений и обновляемая криптографическая проверка необходимы отдельно. Требования применяются к клиентам, заявляющим соответствующую совместимость PLITAP.

## 14. Вопросы для обсуждения

Перед подготовкой стабильной версии необходимо уточнить:

- место сетевого `tile_id` в упаковке и его связь с паспортом;
- минимальную структуру блока страницы и безопасное отображение неизвестных видов блоков;
- связь `parts` и `protected_parts`, область вычисления хеша и размера зашифрованных материалов;
- форму ссылок `proof_refs` и состав подписываемых данных;
- разделение предложения передачи и подтверждения закрепления получателя;
- начало отсчёта сроков, предел повторных попыток и срок действия после дальнейшей передачи;
- состав достаточной истории и материалов автономного архива;
- стабильное базовое представление для совместимости разных поколений клиентов.

Эти вопросы будут уточняться при обсуждении формата и проработке основных типов плиток.
